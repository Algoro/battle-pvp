# 3D-вид: альтернативный рендер (display-only патч)

> Статус: **проект** (не реализовано). Цель — добавить альтернативный трёхмерный
> вид игрового поля с масштабированием и вращением, **не меняя игру**: ни RAM,
> ни кадры ядра, ни rollback/desync/хэши, ни ROM-патчи и их fingerprint.

## 1. Постановка задачи

- Новая графика: процедурные 3D-модели танков, стен, орла (базы), воды/льда/деревьев,
  призов, пуль и эффектов.
- Вид сверху в 3D с управлением камерой: **масштаб (zoom)** и **вращение по разным
  плоскостям** — рыскание (Yaw), наклон (Pitch), крен (Roll), плюс панорамирование.
- Патч — **только отображение**: он читает авторитетное состояние (RAM/PPU) и рисует
  его. Никакой обратной связи в симуляцию.

## 2. Место в архитектуре: драйвер рендерера

3D-вид — **не игровой патч** и не «режим» внутри ядра, а **`RenderDriver`** в новом
слое рендера (`docs/render-extensions.md`). Здесь — его конкретная реализация,
`topdown-3d`, первая из альтернативных драйверов.

Следствия (полностью соответствуют инвариантам слоя рендера):

- **не** регистрируется в `shared/features.ts` и **не** входит в набор патчей
  (`applyPatchSet`, fingerprint, handshake, `match.start`); его метаданные — в
  `shared/renderers.ts` (`kind: "driver"`, `provides: ["three","camera","overlay-dom"]`);
- **не** пишет в RAM, не трогает ввод, `stepFrame`, `saveState/loadState`, `getFrameHash`;
- выбирается **каждым клиентом локально** (соло, онлайн и spectator), а не хостом;
- изолирован в `frontend/src/render/`; `emulator-core`, `netcode`, `backend` о нём не знают;
- совместимые расширения (`particles`, `minimap`, …) подключаются поверх него хостом
  `RenderSystem`; несовместимые — пропускаются.

Тогда переключение драйверов гарантированно не влияет на исход матча: рендер никогда
не вызывает `stepFrame`, а получает только read-only `SceneState`.

## 3. Архитектура

```

frontend/src/
  engine/

    render/

      registry.ts          registerRenderer / resolveDriver / resolveExtensions + assert
      render-system.ts     RenderSystem: композиция driver + [extensions], lifecycle
      camera-rig.ts        общая модель камеры (yaw/pitch/roll/zoom/pan)
      scene-state.ts       readScene(emu): SceneState — ЧИСТОЕ извлечение (RAM)
      drivers/

        topdown-3d/        ЭТОТ драйвер

          textures.ts      палитра NES + процедурные текстуры
          models/
            tank.ts        танк (DEF/ATT, 4 класса, гусеницы, башня, звёзды, каска/стан)
            terrain.ts     кирпич (квадранты!), сталь, вода, лёд, деревья, дорога
            base.ts        орёл: цел / разрушен / укреплён (лопата)
            props.ts       пули, призы (6 иконок), взрывы, спавн-маркеры, точки pacman
      extensions/
        particles.ts       пример расширения к topdown-3d (three)
        minimap.ts         пример DOM-оверлея (overlay-dom)
  components/
    GameCanvas.tsx         контейнер <RenderSystem> + RenderSettings
    SpectateView.tsx       то же для наблюдателя
    RenderSettings.tsx     выбор драйвера + расширений (локально, не в сеть)
```

`EmulatorDriver` больше не рисует кадр: игровой тик вызывает `render.frame(dtMs)` у
`RenderSystem`, который провайдером получает `readScene(emulator)`. Это покрывает соло
(`step`), онлайн (`advance`/`draw`) и spectator одним путём, без изменения сетевого цикла.

## 4. Извлечение состояния (без побочек)

Переиспользуем готовый семантический слой `emulator-core/model/game-view.ts`
(`readState(mem)` → танки/пули/призы/орёл/поле). Обёртка `scene-state.ts`:

```ts
export interface SceneTank {
  index: number; team: "DEF" | "ATT";
  x: number; y: number;          // RAM-пиксели; мир = /8
  dir: 0 | 1 | 2 | 3;            // Up/Left/Down/Right
  state: "alive" | "spawning" | "exploding" | "dead";
  type: number;                  // 0x80/0xa0/0xc0/0xe0, bit 0x04 — мигающий
  stars: 0 | 1 | 2 | 3;          // DEF upgrade
  helmet: boolean; stunned: boolean; onIce: boolean;
  flashing: boolean; lives?: number;
}
export interface SceneState {
  frame: number;
  field: Uint8Array;             // 32×32 тайлов коллизий (копия)
  bounds: { cols: number; rows: number }; // видимая игровая зона (26×26)
  tanks: SceneTank[];
  bullets: { owner: number; team: "DEF"|"ATT"; dir: number; x: number; y: number }[];
  prize: { id: number; x: number; y: number } | null;
  eagle: { col: number; row: number; fortified: boolean; destroyed: boolean };
  effects: { freezeTimer: number; dotsLeft: number | null };
  events: RenderEvent[];         // дельты кадра (взрывы/попадания) для эффектов
}
export function readScene(emu: EmulatorDriver): SceneState; // чистая, без записи
```

- Координаты: RAM-пиксель `x,y` → мир `(x/8, y/8)`; клетка буфера 8×8 px = 1 юнит.
  Поле 32×32, но видимая зона — 26×26 клеток (13×13 блоков ROM); границы сверяем с
  `getStage()`/`StagePreview` и оставляем настраиваемыми.
- `events` — только для визуальных эффектов (детект переходов flag→0x73, bullet→0x33,
  brick destroyed, prize spawn/pickup). Считаются из prev/current срезов; в RAM не пишут.
- `readScene` **никогда** не вызывает `stepFrame` и не мутирует `mem`.

## 5. 3D-модели (процедурные, low-poly)

Никаких внешних ассетов. Геометрия из примитивов three.js, материалы MeshStandard/Lambert,
палитра NES. Идентичность Battle City сохраняется силуэтами.

### 5.1 Танк (`models/tank.ts`)
Группа: `hull` (корпус, слегка скошенный), `turret` (сфера/цилиндр), `barrel` (цилиндр),
`tracks[2]` (коробы с «траками» — повторяющиеся сегменты), командная полоса (DEF/ATT).
- Направление `dir`: поворот группы (Up/Left/Down/Right).
- Классы ATT: базовый (0x80), быстрые пули (0xa0), быстрый (0xc0, вытянутый корпус),
  бронированный (0xe0, +щитки, металл, индикатор брони по `hitsLeft`).
- Мигающий бонусный враг (`type & 0x04`): мерцающая эмиссия/полоса.
- DEF: 0–3 звезды на башне (`RAM.TANK_UPGRADE`); каска (`HELMET>0`) — полупрозрачный
  купол; стан (`STUN>0`) — вращающиеся «звёздочки» над танком; лёд (`onIce`) — лёгкий
  виляющий наклон.
- Гусеницы анимируются по `RAM.TANK_WHEELS` (сдвиг UV/сегментов) — визуально, не в RAM.

### 5.2 Окружение (`models/terrain.ts`)
- **Земля**: тёмная плоскость + сетка; дорожные тайлы (0x20..0x7f) — плиты другого тона.
- **Кирпич**: *важно* — значение тайла это битовая маска 4 квадрантов
  (bit0 TL, bit1 TR, bit2 BL, bit3 BR). Модель собираем из 4 четверть-боксов, показываем
  только установленные биты → разрушение в 3D **точно совпадает** с логикой `brickHit`.
  Материал кирпично-красный, лёгкая неровность.
- **Сталь (0x10/0x11)**: металлический блок с фаской и заклёпками, выше кирпича.
- **Вода (0x12)**: анимированная плоскость (scroll нормалей/UV), полупрозрачная, проходит танк.
- **Лёд (0x21)**: глянцевая светлая плита (низкая roughness), лёгкий блик.
- **Деревья (0x22)**: кластер низкополигональных крон; выше танка, чтобы укрывать
  (в original кусты скрывают) — рисуем поверх с небольшой прозрачностью.
- **Орёл/база** (`models/base.ts`): постамент + орёл; состояния — цел (золото),
  разрушен (серый, «сломанный», при `game_over`), укреплён (стальной купол/клетка,
  `RAM.FORTIFIED>0`). Позиция — из `eagle` (поиск EAGLE-тайлов).

### 5.3 Объекты (`models/props.ts`)
- **Пуля**: маленькая светящаяся капсула, ориентирована по `dir`, эмиссия + лёгкая пульсация.
- **Призы (id 0..5)**: парящая вращающаяся иконка по мотивам ROM: каска(0), часы(1),
  лопата(2), звезда(3), граната(4), жизнь/танк(5). Позиция из `PRIZE_X/Y`, bob-анимация.
- **Взрывы**: короткий частичный burst/расширяющийся спрайт по `events` (танк/пуля/кирпич/HQ).
- **Спавн-маркер**: вращающийся знак в точке появления врага (флаг respawn 0xe0).
- **Pac-Man** (опц.): точки — мелкие светящиеся пилюли (Instanced), бомбы — иконки призов.

## 6. Камера и управление (масштаб + вращение по разным плоскостям)

`camera-rig.ts` хранит `{ yaw, pitch, roll, distance, target }`, считает положение
камеры на сфере вокруг `target` и применяет `roll` кватернионом.

Ручки управления:
- **Мышь**: ЛКМ — орбита (yaw/pitch), ПКМ/Shift — панорама, колесо — zoom.
- **Тач**: 1 палец — орбита, 2 пальца — pinch-zoom + панорама.
- **Клавиатура**: Q/E — yaw, R/F — pitch, Z/C — roll, +/- — zoom, Space — reset.
- **Панель `View3DControls`**: слайдеры Zoom, Yaw, Pitch, Roll + *Tilt поля* по X/Y/Z
  (вращение самого поля, а не только камеры) и пресеты «Сверху», «Изометрия», «Свободно».

«Вращать по разным плоскостям» реализуем двумя способами одновременно:
1. **Yaw/Pitch/Roll камеры** — орбита по трём осям;
2. **Euler-поворот корня сцены** (`fieldRotation x/y/z`) — наклонить само поле
   (например, положить «стол» под углом), не трогая камеру.

Clamp pitch (чтобы не уйти под пол), свободный yaw, roll ±180°. Плавное демпфирование
в rAF рендер-петли (только визуал, без шага ядра).

## 7. Интеграция в рендер-цикл

- Драйвер монтируется в контейнер `RenderSystem` и сам создаёт нужный canvas/DOM
  (WebGL-контекст несовместим с 2D на одном canvas — поэтому у `pixel-2d` и `topdown-3d`
  свои элементы, хост переключает видимость).
- `topdown-3d` ленив: `three` подгружается при первом выборе драйвера (`load()` в
  реестре), базовый бандл 2D не растёт. Нет WebGL → `RenderSystem` откатывается на
  `pixel-2d` с уведомлением.
- Сцена обновляется из игрового тика через `render.frame(dtMs)`; внутренний rAF драйвера
  отвечает только за анимации/камеру. Двойного `stepFrame` нет.
- Выбор драйвера/расширений персистится (`bc_renderDriver`, `bc_renderExtensions`) и
  общий для `GameCanvas` и `SpectateView` через `RenderSettings`.

## 8. Производительность

- Поле — статика: `InstancedMesh` для кирпича/стали/деревьев/дороги; пересборка только
  при изменении буфера (dirty-диффы, не весь кадр).
- Один directional + ambient light; тени выключены по умолчанию (тумблер).
- Танки/пули/призы — небольшое число объектов; точки pacman — Instanced.
- Цель — стабильные 60 fps при 8 танках.

## 9. Инварианты и их проверка тестами

- **Игра не меняется**: тест `emulator-core`: два прогона одинаковых входов, в одном
  между кадрами вызывается `readScene`, в другом — нет; `getFrameHash()` и байты
  `saveState` совпадают.
- **SceneState детерминирован и чист**: `readScene(mem)` не мутирует вход; одинаковый
  mem → одинаковый снимок (юнит-тесты `frontend/tests/scene-state.test.ts`).
- **Архитектурный enforcement** (`qa/tests/architecture.test.ts`): модули `render3d/*`
  не импортируются из `emulator-core`/`netcode`/`backend`; `emulator-core` не зависит от
  `three`/DOM; «нет `.js` вне jsnes src» сохраняется.
- `camera-rig.ts` — чистые функции позы/клампов (`frontend/tests/camera-rig.test.ts`).

## 11. Риски / открытые вопросы

- **Границы игрового поля**: буфер 32×32 (8 px), но стадия 13×13 блоков (16 px).
  Нужно точно определить видимую зону и смещение HUD, сверив с `StagePreview`/nametable.
  Решение: вычислять bounds из стадии + отдельная настройка.
- **WebGL vs 2D canvas**: разные контексты → отдельные `<canvas>`.
- **Онлайн**: единственный путь отрисовки (`o.draw()`), рендер-петля не должна шагать ядро.
- **Бандл**: `three` ~600 КБ — только динамический импорт при включении 3D.
- **Лицензии**: `three` (MIT) добавить в `THIRD_PARTY.md`/`package.json`; ROM/ассеты не
  используются — текстуры процедурные (при желании — из `getChrTilePixels`, но это ROM
  только в памяти, не распространяется).
- **Мобильная производительность** и поведение при потере WebGL-контекста (откат на 2D).
