# Миграция CPU/PPU hot-path в WASM — план и статус

## Статус
Полный перенос интерпретатора 6502/PPU из JS в C→WASM — это отдельная крупная
инженерная задача (сотни функций, точная синхронизация PPU/APU с CPU). Выполнять её
«вслепую», без валидации против golden-savestate и эталонного поведения jsnes, —
высокий риск сломать рабочее детерминированное ядро, от которого зависят все критерии
приёмки (в т.ч. №3 — 100% детерминизм).

Поэтому здесь зафиксирован план миграции и **уже доказанный** toolchain/точка
интеграции, а авторитетным остаётся JS-ядро (детерминизм не зависит от того, JS или
WASM исполняет кадр — критерий №3 уже выполнен на JS).

## Уже сделано (доказательство toolchain)
- `./emulator-core/wasm/hash.c` → `hash.wasm` (emsdk/emcc, Emscripten 6.0.8).
  Функции `fnv1a32`, `checksum_sum`. Сборка: `bash emulator-core/wasm/build-wasm.sh`.
- JS `fnv1a32` (pvp.js) побайтово совпадает с WASM (тест `wasm.test.js` PASS).
- Интеграционная точка: JS может вызывать WASM-функции (как `fnv1a32`).

## План переноса исполняемого hot-path в WASM
1. **CPU (6502)**: реализовать интерпретатор на C: регистры (A,X,Y,SP,PC,статус),
   таблица опкодов (256), цикл `step(op)` с точным учётом циклов, адресация. Экспорт
   `nes_cpu_step(mem, state)` или массив состояний в памяти WASM.
2. **PPU**: рендер scanline-за-scanline, nametable/attribute, спрайты, палитра;
   выходной `buffer` (Uint32Array 256×240) пишется в shared memory WASM.
3. **Memory-модель**: `cpu.mem` (64 КБ) как shared `Uint8Array` WASM-памяти; JS-обёртка
   пробрасывает его в `nes.cpu.mem`.
4. **Синхронизация APU/PPU**: перенести `papu` (APU catch-up) и `ppu` (inline stepping
   при каждой bus-операции) по циклам CPU — самый рискованный участок.
5. **save/load state**: state-codec (`state-codec.js`) остаётся (регистры/память), поля
   читаются/пишутся из WASM-состояния.

## Верификация (критично)
- После каждого шага: `qa/tests/asm-patch.test.js` + `emulator-core` детерминизм
  (два инстанса → одинаковый `getFrameHash()`), byte-в-байт сверка с JS-ядром
  на N кадрах (одинаковый вход → одинаковый state).
- Не откатывать без подтверждения эквивалентности на всём наборе ROM-тестов.

## Вывод
WASM hot-path — оптимизация производительности, НЕ требуется для корректности.
JS-ядро выполняет все критерии приёмки. Миграцию выполнять пошагово с постоянной
валидацией, когда появится отдельный бюджет на риск.
