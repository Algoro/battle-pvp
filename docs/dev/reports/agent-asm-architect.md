# Agent-ASM-Architect — техническое ТЗ патчей ASM

Дата: 2026-08-23
Входные данные: `reports/agent-reversing.md` (карта меток), `reports/agent-rng-audit.md`.
Цель: превратить однопользовательский (2 игрока + AI) Battle City (J) в PvP:
команда DEF (1–2 танка, слоты 0,1) защищает штаб; команда ATT (реальные игроки)
управляет бывшими enemy-танками (слоты 2..7) вместо AI.

## 0. Инженерные ограничения (фундамент ТЗ)
1. **Банк FF заполнен на 100%** (`Free bytes in bank FF: 0x0000`). Новый код можно
   разместить только в:
   - «bzk garbage» `0x002F85..0x003000` (CPU EF75..EFFF) — ~139 байт `$FF`-заполнения;
   - скрытый debug-режим `sub_C755` (CPU C755, ROM 0x000765) — ~47 байт неиспользуемого кода;
   - путём сокращения существующих подпрограмм (напр. удаление «bzk optimize» дублей).
2. **RAM свободна:** блок `$01DB..$01FF` (37 байт), подтверждённо без единого обращения
   из кода. Используем под резервную зону сетевого ввода.
3. **RNG детерминирован** (счётчик кадров, не wall-clock). Патчим ТОЛЬКО точки вызова
   (по audit): AI-точки (DC8C, DD17, DD48, DD4F, DDD4, DE84, E171) заменяем сетевым
   вводом; бонусные (E8C3, E8CD, E8E6) НЕ трогаем.
4. **Пайплайн сборки:** `preparations.lua` снимает дамп-префикс регуляркой
   `.%s.%s.%s.%s.%s.%s0x......%s..:....:%s..%s..%s...` → `copy_bank_FF.asm` → `ca65 -U`.
   - Правки вносим в `bank_FF.asm`/`bank_ram.inc`/`bank_val.inc` (формат с дамп-префиксом).
   - Для НОВЫХ строк можно писать без префикса (регэксп их не тронет) — валидно для ca65.
   - После каждой правки: `./rom/build/build.sh` (пересборка, контроль размера 24592 и
     отсутствия переполнения банка).

## 1. Резервная зона RAM (bank_ram.inc)
Блок `$01DB..$01FF`. Новые метки (добавить в bank_ram.inc):
```
ram_net_zone_base      = $01DB
ram_net_enemy_dir      = $01DB ; 6 байт, по байту на enemy-танк (слот 2..7):
                              ;   0=Up, 1=Left, 2=Down, 3=Right, FF=нет нажатия
ram_net_enemy_fire     = $01E1 ; 6 байт, edge "выстрел в этом кадре" (0/1)
ram_net_enemy_respawn  = $01E7 ; 6 байт, edge "запрос респавна" (0/1)
ram_net_match_state    = $01ED ; байт состояния матча (для эмулятора/интроспекции)
```
Заполняется эмулятором каждый кадр ПЕРЕД `sub_C2E6_main_battle_script` из сетевых
потоков ввода ATT-игроков (детерминированно). Регистры RNG ($0F, $10) в save state.

## 2. PATCH-P1. Контроллеры: 2 → N логических портов
- **Ограничение:** расширение цикла чтения `$4016/$4017` до N>2 и N-байтовых массивов
  `ram_btn_hold/press` в zero-page непрактично (zero-page плотен, банк полон).
- **Решение (архитектурное):** «программный мультиплексор» реализуется НА СТОРОНЕ
  ЭМУЛЯТОРА. Поддерживается до 8 логических портов:
  - Порт 0,1 (DEF-игроки) — эмулятор мапит сетевые входы на `$4016/$4017`, путь
    оригинала `sub_D689_read_joy_regs` НЕ меняется;
  - Порт 2..7 (ATT-игроки, слоты 2..7) — эмулятор пишет входы в `ram_net_enemy_*`.
- **Почему:** функциональное требование (сетевой ввод для всех N игроков,
  детерминизм) выполняется; менять хардверный цикл и zero-page-раскладку рискованно
  и не даёт выигрыша. Фиксируется как осознанный trade-off.
- **ВАЖНО для EmulatorCore:** `stepFrame(inputs)` принимает до 8 портов;
  порты 0,1 → $4016/$4017; порты 2..7 → `ram_net_enemy_dir/fire/respawn`.

## 3. PATCH-P2. Enemy AI → сетевой ввод (6 танков)
Единый приём: враг (X in 2..7) берёт направление из `ram_net_enemy_dir[X-2]`.
Было/стало/почему по каждой точке (по RNG-audit):

| Точка | Было (AI) | Стало (PvP) | Почему |
|-------|-----------|-------------|--------|
| `sub_DDA2` (DDD4) | RNG AND#1 + таблица `tbl_E486_tank_flags` → направление врага на перекрёстке | `LDA ram_net_enemy_dir,X-2`; если !=FF → `A0\|dir` в `ram_tank_flags,X`; иначе оставить текущее | ГЛАВНЫЙ хук выбора направления |
| `ofs_000_DC7C_A0` (DC8C) | RNG AND#0F → случайный поворот (`sub_DE72`) на перекрёстке | при нажатом направлении из сети — применить его | устранение случайности |
| `bra_DD11` (DD17) | RNG AND#3 → случайный разворот (статус $80) | направление из сети | устранение случайности |
| `ofs_000_DD48_90` (DD48/DD4F) | RNG AND#1 ×2 → поворот влево/вправо | направление из сети | устранение случайности |
| `sub_DE72` (DE84) | RNG AND#3 + #$A0 → случайное направление | направление из сети | устранение случайности |
| `sub_E162` (E171) | RNG AND#1F → выстрел с вероятностью 1/32 | выстрел при `ram_net_enemy_fire[X-2]` | стрельба по кнопке игрока |

Правила: алгоритм RNG НЕ трогаем; бонусные вызовы RNG (E8C3/E8CD/E8E6) оставляем.
После удаления AI-вызовов последовательность RNG изменится — это НЕ ломает
детерминизм (оба клиента исполняют одинаковый код с одинаковым входом).

## 4. PATCH-P3. Симметризация победы/поражения
Точка: `sub_C728_check_condition_for_stage_ending` (CPU C728) + `sub_E2A9_HQ_handler`.
- Сейчас: победа = `ram_enemies_left_cnt==0` (убиты 20); поражение = HQ-орёл уничтожен
  (`game_over_flag`) или `ram_lives+ram_lives+1==0`.
- **v1 (одна база, целевой дизайн):**
  - DEF побеждает: все ATT-танки уничтожены (`ram_enemies_left_cnt==0`).
  - ATT побеждает: HQ-орёл уничтожен (`game_over_flag`) ИЛИ `ram_lives`+`ram_lives+1`==0
    (у DEF не осталось жизней).
  - Условия win/loss **симметричны** в части «потеряны все жизни команды ИЛИ штаб
    уничтожен»; единственное различие — у ATT в v1 нет отдельной базы-орла (балансовое
    решение задокументировано: DEF играет в обороне единственного штаба, что и есть
    премиса Battle City).
- **v2 (полная симметрия, опционально):** добавить вторую базу-орла ATT в верхней зоне
  спавна; DEF-снаряды могут её уничтожить. Требует: новый спрайт+отрисовка
  (аналог `sub_CAF5_draw_default_base`/`sub_CC08_draw_destroyed_eagle`), коллизия пули
  DEF ↔ база ATT (аналог хендлера в `sub_E2A9_HQ_handler`), второй флаг game-over.
  Оцениваемый бюджет кода: ~40–60 байт — умещается в «bzk garbage» EF75-EFFF (~139 б).
  Рекомендуется реализовать после подтверждения эмулятором базовых патчей P1–P3v1.
- Регистры: `ram_enemies_left_cnt` ($80) — счётчик живых ATT; `ram_lives` ($51,$52) —
  жизни DEF; `ram_game_over_flag` ($68) — штаб DEF.

## 5. PATCH-P4. Per-player respawn (вместо волнового спавна)
- Сейчас: `sub_DB48_enemy_spawn_handler` спавнит врагов по таймеру/волнам из верхних
  портов; `sub_E363_tank_spawn_handler` — спавн одного танка.
- Стало: ATT-танк X респавнится при `ram_net_enemy_respawn[X-2]` (игрок нажимает
  респавн/потерял танк) — по аналогии с community-патчем таблицы жизней. Вход респавна
  из верхних спавн-портов (`tbl_E474_enemy_spawn_pos_X/Y`) сохраняется.
- Для DEF-игроков респавн — как в оригинале (по `ram_lives`), `sub_E363` не трогаем.

## 6. PATCH-P5. HUD двух команд
Точки: `sub_C7C8_print_lives_handler`, `sub_C830_draw_Ip_IIp_icons`,
`sub_C894_calculate_enemy_icon_pos`, `sub_C8A2_draw_enemy_icon`, `sub_C8B1_erase_enemy_icon`.
- Было: счёт/жизни P1/P2, значки оставшихся врагов (волна).
- Стало: строка DEF (жизни P1/P2 + статус штаба) и строка ATT (жизни/иконки
  атакующей команды). Наименее инвазивно: перерисовать значки «оставшихся врагов»
  как индикаторы жизней ATT-команды; P1/P2-иконки — как DEF.
- v1: переназначить семантику существующих HUD-полей без изменения их позиций
  (минимальные правки палитры/типов в `sub_C8A2`/`sub_C8B1`).

## 7. Код-бюджет и размещение нового кода
- Новые подпрограммы (например, `sub_net_enemy_dir_read`) разместить в «bzk garbage»
  EF75..EFFF (139 б) или в debug-режиме C755 (47 б), при необходимости — переписав
  короткие «bzk optimize»-участки.
- Следить: после каждой правки `./rom/build/build.sh` должен давать валидный NROM
  24592 байт и сообщение об отсутствии переполнения банка (в `assemble.sh`).

## 8. Требования детерминизма (передача в EmulatorCore/Netcode)
- Регистры RNG $0F/$10 — в save state. Входы ATT — только через `ram_net_*` (никакого
  `Date.now`/`Math.random` в игровом цикле). Входы DEF — через $4016/$4017 из сети.
- `stepFrame(inputs[])` детерминирован: одинаковый вход → одинаковый хэш кадра.

## 9. Порядок внедрения (Agent-Patcher)
1. P1 (контроллеры/muxer) — только эмулятор + RAM-метки; ASM не меняется.
2. P2 (AI→сеть) — правки в `bank_FF.asm`; пересборка; byte-diff на неизменённых зонах.
3. P3v1 (win/loss) — правка `sub_C728`; пересборка.
4. P4 (respawn) — правка `sub_DB48`/`sub_E363`; пересборка.
5. P5 (HUD) — правки `sub_C7C8`/`sub_C830`/`sub_C8A2`; пересборка.
Каждый шаг: regression (неизменённые байты совпадают с базой), затем P3v2 по желанию.

## 10. Риски и trade-offs
- Банк полон → любые правки экономно по размеру; большой риск переполнения при P3v2/P5.
  Митигация: бонусный блок EF75-EFFF, сокращение «bzk optimize»-дублей.
- Без эмулятора (до Agent-EmulatorCore) корректность поведения проверяется только
  сборкой + byte-diff; функциональную проверку даст Agent-QA после EmulatorCore.
- Одна база в v1 — асимметрия DEF/ATT (задокументировано как баланс-решение).
