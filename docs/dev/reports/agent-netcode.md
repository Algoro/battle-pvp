# Agent-Netcode — rollback netcode (аналог GGPO)

Дата: 2026-08-23
Вход: `reports/agent-emulator-core.md` (детерминированное ядро), `reports/agent-patcher.md`.
Результат: **критерий приёмки №4 подтверждён** — два клиента с задержкой ~100 мс
(и джиттером) сходятся без desync, rollback корректно переигрывает кадры.

## Структура (относительные пути)
```
./netcode/
  protocol/frame.js        бинарный формат фрейма ввода + hash-check (не JSON)
  rollback/session.js      RollbackSession (GGPO: предсказание, ring-buffer, rollback, replay)
  transport/transport.js   интерфейс { send, onMessage }
  transport/local.js       in-process транспорт (задержка/джиттер/потери, детерм. PRNG)
  transport/webrtc.js      WebRTC DataChannel (основной P2P-транспорт)
  transport/relay.js       relay-транспорт через backend (fallback при симметричном NAT)
  index.js                 экспорт
  tests/rollback.test.js   интеграционные тесты (критерий №4)
```

## Протокол (Блок 5)
- **Формат фрейма ввода — компактный бинарный (не JSON):**
  `uint32 frame | uint8 count | per-port: uint8 port | uint8 buttons`.
  Кнопки — битовая маска con_btn (совпадает с ядром и ROM).
- `encodeFrame/decodeFrame`, `encodeHashCheck/decodeHashCheck` — в `protocol/frame.js`.

## Rollback-сессия (Блок 5)
- **Предсказание недошедшего входа** = «повтор последнего известного ввода соперника»
  (`_predictedRemote()`).
- **Ring-buffer состояний** (`states[frame] = game.saveState()`), окно `window` кадров.
- **Rollback**: при позднем вводе для уже симулированного кадра — `game.loadState()`
  и переигровка вперёд с буферизованными/предсказанными входами.
- **Desync detection**: периодически шлём `getFrameHash()` ТОЛЬКО для подтверждённых
  кадров (в прошлом, за `confirmDelay`), сравниваем на приёмнике; расхождение — событие
  `{type:'desync', frame, localHash, remoteHash}` и `desyncCount++`.

## Транспорты
- **local** — для тестов: задержка (кадры), джиттер (±), потери (0..1), с
  детерминированным LCG-PRNG. `send()` ставит сообщение в очередь СОПЕРНИКА
  (delivery на его кадре/часах).
- **webrtc** — WebRTC DataChannel (бинарные сообщения), конформно интерфейсу.
- **relay** — через backend-сигналинг (WS, base64 payload), fallback при NAT.

## Ключевые найденные и исправленные ошибки
1. **Транспорт отдавал сообщения самому себе** — `send()` писал в собственную очередь;
   исправлено на постановку в очередь соперника.
2. **Не пересохранялись состояния при re-симуляции** — `states[k]` после rollback
   содержал устаревший снимок от предсказанной симуляции; при повторном откате к `k`
   восстанавливалось неверное состояние → рассинхрон. Исправлено: в цикле re-игры
   `states[f]` пересохраняется перед каждым кадром.
3. **Ложные desync** от сверки хэша не подтверждённых (ещё не согласованных) кадров —
   теперь хэши сравниваются только для подтверждённых кадров.

## Тесты (все PASS)
- Критерий №4: два клиента, задержка 6 кадров (~100 мс) + джиттер 1, 120 кадров →
  **одинаковый финальный `getFrameHash()`, `desyncCount == 0`, rollback > 0**.
- Без задержки: оба идентичны, десинк 0.
- Детект десинка: искусственный рассинхрон фиксируется событием `desync`.

## Примечание по производительности (решено)
Ранее `game.saveState()` (эмулятор) использовал JSON-сериализацию полного образа
(64 КБ `mem` как массив чисел) — это делало rollback-тесты ~30-50 с. После
**оптимизации Agent-EmulatorCore** (бинарный state-codec) saveState ускорился
с 15.2 мс до 0.46 мс, loadState с 5.8 мс до 0.14 мс; полный набор netcode-тестов
(~270 кадров rollback) упал с ~100 с до ~7 с.

## Передача управления
**Agent-Backend**: релей WebRTC-сигналинга + relay-транспорт; **Agent-Frontend**:
запуск сессий в браузере, рендер, индикатор rollback; **Agent-QA**: нагрузочное
тестирование комнат и джиттера/потерь (используя `LocalEndpoint`).
