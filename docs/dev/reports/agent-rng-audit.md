# Agent-RNG-Audit — аудит генератора случайных чисел

Дата: 2026-08-23
Объект: `sub_D44D_generate_random_number` (CPU D44D, ROM 0x00145D) в `./rom/disasm/bank_FF.asm`.
Зависит от: `bank_FF.asm`, `bank_ram.inc` (регистры), `bank_val.inc` (константы).

## 1. Алгоритм RNG (вывод)
```
PHA
LDA ram_random          ; $000F
ASL ×3                  ; = ram_random << 3
SEC; SBC ram_random     ; = (ram_random<<3) - ram_random = ram_random * 7
CLC; ADC ram_frm_cnt_hi ; $000A — счётчик кадров (высокий байт, +1 каждые 64 кадра)
INC ram_index_for_random; $0010
LDX ram_index_for_random
ADC $00,X               ; + нулевая страница[ram_index_for_random]
STA ram_random          ; новое значение
...
LDA ram_random; RTS     ; A = RNG-результат
```
Тип: комбинированный PRNG (линейная комбинация регистра, счётчика кадров и
zero-page), не классический LFSR, но семантически то же — псевдослучайный генератор.

## 2. Детерминизм (критично для rollback netcode)
- **Источники энтропии RNG:** `ram_random` ($0F), `ram_index_for_random` ($10),
  `ram_frm_cnt_hi` ($0A), содержимое нулевой страницы. **ВСЕ они — детерминированные
  состояния NES, НЕ wall-clock время.**
- `ram_frm_cnt_hi`/`ram_frm_cnt_lo` инкрементируются в NMI (`vec_D400_NMI`, D43C)
  **ровно один раз за кадр** — это детерминированный счётчик кадров эмулятора.
- Единственный «внешний» вход игры — состояние контроллеров ($4016/$4017),
  которое в нашем эмуляторе берётся из сетевого потока входов (детерминированная
  последовательность). В оригинале никаких чтений wall-clock/`performance.now`
  нет (проверено: `$4017` только пишется в APU-фрейм-счётчик, строка 7289, чтений нет).
- **ВЫВОД:** RNG полностью детерминирован при условии: (а) фиксированный начальный
  seed (весь RAM обнуляется на RESET, значит `ram_random`=0 на старте), (б) одинаковая
  последовательность входов на двух клиентах. Два независимых инстанса эмулятора с
  одинаковым save-state и одинаковым входом дают одинаковый хэш каждого кадра.
- **Обязательное требование для Agent-EmulatorCore:** регистры RNG `ram_random` ($0F)
  и `ram_index_for_random` ($10) должны входить в save/load state. Поскольку
  save-state = полный образ RAM ($0000..$07FF), это выполняется автоматически, но
  для determinism-тестов явно проверить.

## 4. Рекомендации для Agent-ASM-Architect / Agent-Patcher
- **Правило явное (из ТЗ):** сам алгоритм RNG НЕ менять. Патчить только точки вызова.
- Точки 1–7 относятся к AI вражеских танков → в PvP-режиме они ЗАМЕНЯЮТСЯ на чтение
  байта состояния из зарезервированной RAM-зоны (сетевой ввод атакующей команды).
  Патч именно этих точек безопасен и не влияет на детерминизм при равных входах.
- Точки 8–10 (бонусы) **оставить** — дают детерминированное разнообразие спавна
  бонусов, не участвуют в win/loss и в AI. Сохраняет оригинальное поведение.
- **ВАЖНО про рассинхрон последовательности:** после удаления вызовов 1–7
  (замена на сетевой ввод) последовательность значений RNG изменится относительно
  оригинального ROM. Это НЕ ломает детерминизм: два клиента выполняют ОДИНАКОВЫЙ
  код с одинаковым входом → одинаковая цепочка RNG → одинаковый бонус-спавн.
- **Запрещено:** переинициализировать `ram_random`/`ram_index_for_random` из
  `Date.now()`/`performance.now()`/`Math.random()` в эмуляторе. Seed фиксируется
  на RESET (обнуление RAM), эволюция — только через `sub_D44D` и счётчик кадров.
- `ram_random` и `ram_index_for_random` **обязательно в save state** (для rollback).

## 5. Замечание по rollback-детерминизму (передача в EmulatorCore)
- Поскольку RNG детерминирован, при откате к сохранённому состоянию и повторном
  прогоне кадров с теми же входами генератор воспроизводится байт-в-байт. Это базовое
  условие корректности rollback netcode (GGPO-подход). Проверяется тестом:
  идентичный вход на двух инстансах → идентичный `getFrameHash()` на каждом кадре.
