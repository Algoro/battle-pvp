# Handoff — Network Battle: симулятор и ИИ

Цель этой записки — позволить продолжить работу в новой сессии. Зафиксированы архитектура, что сделано, что проверено, что осталось и как это всё запускать/тестировать.

---

## 1. Контекст проекта
`network_battle` — Battle City PvP: JS-эмулятор NES (`emulator-core`) + фронтенд (Vite) + backend (HTTP/WS). Два направления работы:
- **ИИ** (атакующие/защитники): `tactical-ai.js` (plan), `scan-ai.js`, `lookahead-ai.js`.
- **Точная симуляция эмулятора** (для предсказания ИИ и сверки): `emulator-core/sim/*`.

Запуск:
- `docker build -t battle-city-pvp .` → `docker run -rm -p 8080:8080 battle-city-pvp`
- URL: `/` (игра), `/demo.html` (asm vs plan-защитник), `/demo-sim.html` (симулятор как движок).
- Тесты: `emulator-core`: `node --test tests/*.test.js`; `qa`: `npm test`; `frontend`: `npm test`.

---

## 2. Архитектура слоя симуляции
`emulator-core/game-view.js` — единый слой доступа:
- **A.** `GameState`/`readState(mem)` — модель боя + хелперы (`passable/brick/lineClear/dist/dirTo/cellOf`), примитивы (`isBrick`, `blocksBullet`, `brickHealth`, `brickHit`, `DX/DY`).
- **B.** `buildState({field,tanks,bullets,prize,eagle})` — декларативный билдер для тестов (без адресов RAM).
- **C.** `wrap(emu)` — живой адаптер над эмулятором.
- **D.** `brain-runner.js` — `runBrain(state,prev,mode,role)` — единая точка запуска движков.

`emulator-core/sim/`:
- `sim-model.js` — `canLead(x,y,dir,field)` (точный порт ASM `sub_DC97`), `step`, `traceMovement`.
- `engine.js` — `GameSim`: `stepTank` (субпиксель + поворот при блоке), `fireTank`, `_moveBullet`, `spawnEnemy`, `stepEnemy` (флаг-машина + навигация), `_navigate` (`sub_DDA2`), `_enemyTarget` (`sub_DE72`).
- `cycle.js` — `CycleSim`: абстрагированный цикл кадра (порядок процедур из `sub_C2E6`): `ice→tank→bullets_status→hq→enemy_spawn→bullets_movement→bullet_vs_bullet→bullet_vs_tank→bonus→enemy_death→player_death→stage`. Микро-события.
- `observer.js` — `EmuObserver`: пассивный читатель `mem` эмулятора, эмитит те же события, **не влияет на ИИ** (хеш игры не меняется).

## 3. Что проверено (покадрово против эмулятора)
- **Движение танка** `canLead` = точный порт `sub_DC97` (коллизия передней кромки, 2 точки + клампинг).
- **Разрушение кирпичей** `brickHit(tile,dir)`: 4 квадранта (`bit0=TL,1=TR,2=BL,3=BR`), пуля убирает половину, обращённую к ней. Проверено с 4 сторон: `0x0f→0x03/0x0c/0x0a/0x05→0x00`. Кадр разрушения совпадает (f9=f9).
- **Движение пули**: 2px/кадр (откалибровано), хитбокс пули-в-танк = `|dx|<10 && |dy|<10` (ASM `sub_E70C`).
- **Субпиксельный темп движения**: игрок 0.75px/кадр (кроме `frame%4==2`), обычный враг 0.5px/кадр (`(index^frame)&1`), power-враг 1px/кадр.
- **Скорость игрока**: 45px/60 кадров = точно как эмулятор.

## 4. Важные находки/исправления
- **`isBrick` был неправильный**: сталь (0x10/0x11) ошибочно считалась кирпичом. Исправлено: кирпичи = {0x0f, 0x0c, 0x03, 0x13, 0x14}, сталь = {0x10, 0x11} (не разрушается).
- **RNG-инжекция**: `PvPNes.setRngInjection(value)` — ловушка на `sub_D44D` (PC=0xD44D → подставить A, RTS). Методика: **одинаковые RNG-значения в эмулятор и симулятор → чистая проверка логики порта**.
- **Тестовый хук**: `PvPNes.spawnBonus(id,x,y)` — штатный спавн приза (таймер `$62=0`).

### 4a. Точный порт вражеского ИИ (эта сессия, `sim/engine.js`)
По `bank_FF.asm` найдены и исправлены ошибки старой упрощённой модели врага:
- **Навигация `_navigate`**: для врагов используется ТОЛЬКО базовая таблица `tbl_E486` (idx 0..8). Случайная таблица (+9, `loc_DDDB`) — только для ИГРОКОВ. Раньше враг с вероятностью `rng()&1` брал случайную таблицу — неверно.
- **Выбор цели `_pickFollowFlag` (порт `sub_DE72`)**: условие HQ было ИНВЕРТИРОВАНО. ASM: `if (interval>>2 < frm_cnt_hi) -> follow HQ`. Старая модель: `>=` (всегда HQ в тестах).
- **`keep current` вместо random**: ветка `else` в ASM (`sub_net_enemy_dir_store` без сетевого ввода) просто RTS — враг СОХРАНЯЕТ текущее направление. Старая модель возвращала случайное направление.
- **Follow-флаги (0xB0/0xC0/0xD0)** — отдельные промежуточные состояния: следование задаёт направление через `sub_DDA2` и НЕ двигается в этом кадре.
- **Блок**: точные под-состояния ASM — `bra_DD1E` пауза `0x88|dir` (когда `rng()&3!=0`) и `bra_DD30` разворот `dir^2` (когда `rng()&3==0`, на сетке флаг `0x90`, иначе `0xA0|newdir`). Вместо всегда-180°.
- **Ретаргет на пересечении**: при `x%8==0 && y%8==0 && rng()&0x0F==0` ASM ВСЕГДА вызывает `sub_DE72` и возвращается без движения (DC93 JSR; DC96 RTS). Старая модель двигалась, если цель не сменилась.
- **`_enemyGate` (порт `sub_DBF1` DC18-DC38)**: субликсельный темп (включая респавн/взрыв) — `type&F0==0xA0 ? всегда : (idx ^ frm_cnt_lo)&1 != 0`. Обрабатывает таймер заморозки (часы).
- Врагу-без-флага (мёртвый, flag=0) добавлен guard `if (hi===0xa0)` — раньше мёртвый танк «двигался» как 0xA0.

### 4c. Реализация A+B+C: верный порт вражеского боя (`sim/battle.js`)
Новый модуль `BattleSim` — покадрово-верный порт `sub_C2E6_main_battle_script` (вражеская сторона), на патченом ROM (вариант B).
- **A** — детерминированный PRNG `rng()` = порт патченого `sub_D44D`: `$0F=($0F*7+frm_hi+frm_lo)&0xFF`. Никакой PC-инжекции.
- **B** — динамическое поле: bit7-маркеры танков (геометрия `sub_E181`/`sub_E1FA`: 2×2 блок, `+0x21` всегда, `+0x20` при `x&7==0`, `+0x01` при `y&7==0`; маркеры снимаются на той же позиции, где ставились) + разрушение кирпичей пулями.
- **C** — полный кадровый цикл вражеской стороны: движение `sub_DBF1` (флаг-машина + гейт), вражеский огонь `sub_E162` (RNG==0), пули (`sub_E604`/`E910`/`E70C`), спавн (`sub_DB48`/`E363`: таймер, INC-позиции до использования, тип по стадии `sub_E3CB`, флаг респавна всегда 0xF0, бонус — через тип 0x04), смерть/взрыв, приз из мигающего врага (`sub_E8BE`: 2×RNG на позицию + ретрай при наезде + 1×RNG на id).

Харнесс: `scripts/battle-verify.mjs` (эмулятор на патченом ROM vs `BattleSim`), `scripts/level1-verify.mjs` (весь уровень).
Результат: **враги (флаг+поз) 100% на 3875 кадров** (99.1% уровня, RNG синхронен), затем рассинхрон.
Исправлено по ходу доводки: тип врага (`sub_E3CB`/`tbl_E578`), `alive` заспавненных танков, фикс. 10 слотов пуль, флаг респавна 0xF0, **суб-ячеечная коллизия пуль** (`sub_D725`/`sub_D73C`, ширина), проверка текущей+следующей позиции пули, `sub_E420` (направление в follow-флаге), **`gateFrmLo`** (гейт движения на reset-кадрах), **пре-кадровая синхронизация DEF-танков/игроков (0,1)** (маркеры по состоянию на начало кадра, отодвинуло с f3048 на f3582), **`_bonusOnTank`** по `movementRange`.
Юнит-тесты симулятора: `tests/battle.test.js` (13 шт.).

### 4e. Точный split `$0B` для RNG (эта сессия) — RNG синхронен до f3875
`rng()` раньше использовал ЕДИНОЕ значение `$0B` (сначала `gateFrmLo`, потом `frame&0xff`).
Но игра СБРАСЫВАЕТ `$0B` в 0 **в середине кадра** (`sub_DE46_set_message_init_data`, вызывается
при гибели игрока → game-over-сообщение): движения-фаза читает pre-reset `$0B`, фаза огня — 0.
- `gateFrmLo = prevB+1` даёт pre-reset `$0B` (V_f после NMI) → ВЕРНО для фазы движения.
- `frame & 0xff` даёт post-reset `$0B` (=0 на reset-кадре) → ВЕРНО для фазы огня/пуль.
- Раньше одно значение ломало RNG: на reset-кадре с огнём (f2421) и с движением (f3582).
- **Фикс**: `step()` ставит `this._rngLo = gateFrmLo` до фазы движения и `this._rngLo = frame&0xff`
  перед фазой огня; `rng()` читает `this._rngLo`.
- Результат: RNG синхронен и враги 100% на **весь уровень 1 (3912/3912 = 100%)**. Ранее враги
  расходились на f3648/3875.
- Диагностика: `scripts/rng-trace.mjs` — сравнение последовательностей RNG эмулятор/симулятор
  (хук на RTS `sub_D44D` @PC=0xd465, REG_PC на 1 меньше адреса).
Важно: гейт пуль (property 0 → через кадр) НЕ применять — эмулятор движет пули 2px/кадр каждый кадр.

### 4f. Точность пуль и разрушения кирпичей (эта сессия) — враги 100% на весь уровень
Два точечных фикса, устранивших рассинхрон поля → пуль → RNG:
1. **Пуля не движется в кадр выстрела** (`emulator-core/sim/battle.js`): в эмуляторе пуля,
   созданная в `sub_E162`/`sub_E08C`, НЕ двигается в том же кадре (`sub_E604` её не двигает) —
   она остаётся в точке спавна до следующего кадра. Симулятор раньше сразу двигал её на
   BULLET_SPEED (2px), из-за чего пуля оказывалась на 2px впереди и разрушала кирпич на кадр
   раньше → каскад: поле/`canLead`/RNG. Фикс: `_fireEnemy` ставит `b.fresh = true`;
   `_moveBullets` пропускает свежую пулю в этом кадре.
2. **`isBrick` не включал половины кирпичей** (`emulator-core/game-view.js`): набор разрушаемых
   кирпичей был `{0x0f,0x0c,0x03,0x13,0x14}` и НЕ включал `0x0a`/`0x05` (половины кирпича после
   первого попадания). Поэтому вторая пуля по 0x0a/0x05 не разрушала кирпич до конца (сим 0x0a,
   эмул 0x0). Фикс: `isBrick` += `0x0a`, `0x05`.
3. **Гейт проверки коллизии пуль** (`sim/battle.js`, `_moveBullets`): в эмуляторе пулю ДВИГАЕТ
   `sub_E02E/sub_E063` каждый кадр (2px), а КОЛЛИЗИЮ проверяет `sub_E604` с гейтом для property-0
   пуль: `(slot ^ $0B) & 1 != 0` → только на «своих» кадрах. Прежняя реализация проверяла коллизию
   каждый кадр (current+next), из-за чего пуля разрушала кирпич на кадр раньше и «пробивала»
   половинчатые кирпичи (0xc/0x03) в нижнюю/целую половину. Фикс: пуля движется каждый кадр,
   коллизия проверяется на гейт-кадрах. Результат: **поле 99.97% (3911/3912)**, враги 100%.
- Результат: **враги (флаг+поз) совпадают 100% на весь уровень 1 (3912/3912)**, RNG синхронен,
  **поле 99.97%** — остаётся 1 кадр (f3911, конец уровня/переход game-over) с расхождением
  маркерного бита на тайлах штаба `(26-27,14-15)`.
- Побочный эффект `isBrick`: меняет поведение JS-ИИ (lookahead/plan дефолт в golden) —
  golden перегенерирован.

### 4h. Повреждение штаба, лопата, лёд (эта сессия) — поле 100%
Механики, не входившие в сверку уровня 1, добавлены по ASM:
1. **Повреждение штаба/конец стадии** (`sub_E69A`: пуля попала в орла `(tile & 0xFC)==0xC8`):
   `_bulletCollide` вызывает `_destroyHQ()` — рисует разрушенного орла (`sub_CC08_draw_destroyed_eagle`,
   тайлы 0xcc/0xce на (26,14-15), 0xcd/0xcf на (27,14-15)) и ставит `c.gameOver`. Это устранило
   последний 1-кадровый артефакт (f3911, конец уровня по уничтожению штаба): **поле 100% (3912/3912)**.
2. **Лопата/укрепление** (`sub_CB9E_draw_protected_base` + `ofs_bonus_E9FB_02_shovel`): приз-лопата
   (id 2) укрепляет базу сталью 0x10 на клетках `(25,13..16),(26,13/16),(27,13/16)`, орёл C8-CB
   остаётся; таймер `shovelTimer=0x14` (sub_E2A9) декрементится каждые 64 кадра, по истечении база
   восстанавливается. Юнит-тест.
3. **Лёд** (`sub_E181/sub_DB75`): детекция льда в `sub_E181` пропускает врагов (`CPX #$02`), слайд
   (`sub_DB75`) — только для игроков. Для врагов лёд (0x21) уже passable (`tankPassable`), симулятор
   совпадает с эмулятором без изменений. Слайд DEF-игроков — вне скоупа (DEF танки синхронизируются).
4. **DEF-сторона**: DEF-танки (0,1) синхронизируются с эмулятора каждый кадр (позиция/флаг), их
   ИИ/управление вне скоупа `BattleSim` (предсказание врагов).
- Результат: **враги 100% (3912/3912), поле 100% (3912/3912), RNG синхронен** — уровень 1 полностью
  сверен.

### 4g. Стирание иконок врагов (эта сессия)
Тайлы `(12,29)/(11,30)/(11,29)` были `0x6a` в симуляторе против `0x11` в эмуляторе — это
**иконки врагов** в поле (`tbl_D362_tile___enemy_icon = 0x6a`), которые игра стирает при спавне
врага (`sub_DB48 -> sub_C8B1_erase_enemy_icon`, серый/стальной тайл `tbl_D36B = 0x11`).
Позиция иконки индекса i (после декремента spawnCount): `col=(i&1)+29, row=(i>>1)+3`.
Фикс: `_spawnEnemy` после `spawnCount--` вызывает `_eraseEnemyIcon(spawnCount)`.
Результат: **поле 99.8% (3904/3912)** (было 4.1%), враги остались 100%.

### 4i. Сверка уровня 2 + фикс `property` пули (эта сессия)
- **Фикс `property` пули** (`_fireEnemy`): по `sub_E08C` property=0 у типов 0x00/0x80/0xA0/0xE0
  (гейт коллизии), property=1 у 0xC0/0x20/0x40, property=3 у 0x60. Прежнее `(type&0xf0)===0x80?0:1`
  давало неверный property бронированным (0xE0) и power (0xA0) — на уровне 1 (только basic) не
  сказывалось, на уровне 2 (много 0xE0) ломало поле. После фикса **уровень 2: враги 100%, поле 100%,
  RNG синхронен** (6000 кадров), уровень 1 остался 100%.
- **`scripts/stage-verify.mjs [stage]`** — верификация произвольной стадии: форсирует переход на
  целевую стадию (`enemies_left=0` → `sub_C728` завершает стадию → `INC ram_stage`), синкает BattleSim
  на старте и сверяет врагов/поле/RNG. Надёжен для уровня 2; для 3+ переход уходит в demo-режим
  (ограничение харнесса).
- Уровень 2 в этом ROM не содержит льда 0x21 (поле имеет другие твёрдые тайлы), но симулятор совпадает
  на 100%; лёд-механика для врагов корректна по ASM (0x21 passable).

### 4j. Сверка всех стадий + фикс `_tileSolid` (эта сессия)
- **`_tileSolid`**: эмулятор в `sub_E69A` пропускает коллизию пули для тайлов `>= 0x12`
  (`CMP #$12; BCS` — дорога/лёд и т.п.), орёл/штаб (0xC8-0xCB) обрабатывается ДО этой проверки.
  Прежний `_tileSolid` считал дорогу (0x20-0x7F) твёрдой для пуль → пули сима умирали на дороге.
  Фикс: `tile < 0x12 && (tile & (0xf0|sub)) != 0`, плюс орёл как блок.
- **Результат сверки всех стадий** (`scripts/stage-verify.mjs [stage]`, форсирует переход через
  `enemies_left=0` каждый кадр):
  | Стадия | Враги | Поле |
  |---|---|---|
  | 1 | 100% (3912/3912) | 100% |
  | 2 | 100% (6000/6000) | 100% |
  | 3 | 27% (1191/4402) | 27% (1177/4402) |
  | 4 | 28% (1572/5554) | 28% (1555/5554) |
  | 5 | 44% (2585/5914) | 44% (2623/5914) |
  | 6 | 43% (2563/6000) | 42% (2542/6000) |
- Стадии 3+ расходятся: симулятор местами пере-разрушает кирпичи (поле 0x0/0xc против эмулятора
  0xf) и недо-разрушает другие → каскад через `canLead` → расхождение врагов. Глубокая тонкость
  коллизии пуль (порядок/тайминг гейта, соседние ячейки, траектории на новых тайлах).

### 4k. Фиксы стадий 3+ (эта сессия) — isBrick, скорость пули, типы по стадии
- **`isBrick`** (`game-view.js`): разрушаемые кирпичи — ВСЕ тайлы 0x01-0x0F (любые комбинации квадрантов),
  плюс 0x13/0x14. Прежний набор `{0x0f,0x0c,0x03,0x0a,0x05,0x13,0x14}` пропускал мелкие состояния
  (0x1,0x2,0x4,0x8,...) — пули сима попадали в кирпич (tileSolid true) но не разрушали (isBrick false).
- **Скорость пули** (`_moveBullets`): `property & 0x01` → 4px/кадр, иначе 2px (`ofs_E051`: `sub_E063` ×2).
  Быстрые/мощные пули (property 1/3) движутся вдвое быстрее.
- **Типы врагов по стадии** (`_pickType` → `STAGE_TYPE_VALUES`): значение типа из `tbl_E4EC_stage_enemies`
  зависит от стадии (напр. стадия 4: `[0xC0,0xA0,0x80,0xE0]` — первый тип fast). Прежний фиксированный
  `TYPE_VALUES=[0x80,0xA0,0xC0,0xE0]` давал неверный тип/свойство пули на стадиях с другим порядком.
- **Результат сверки стадий** (после фиксов):
  | Стадия | Враги | Поле |
  |---|---|---|
  | 1 | 100% | 100% |
  | 2 | 100% | 100% |
  | 3 | **100%** | 1646/4402 (3 тайла) |

### 4d. Вариант B — патч ROM `sub_D44D` (детерминированный PRNG)
`bank_FF.asm`: в `sub_D44D` заменён page-zero-микс (`INC $10; LDX $10; ADC $00,X`) на `CLC; ADC ram_frm_cnt_lo` (+NOP-пады). Итог: `$0F = ($0F*7 + frm_hi + frm_lo) & 0xFF` — чистый PRNG, независимый от игровой RAM, состояние честно эволюционирует. Враги двигаются (инжекция их замораживала). ROM пересобран (`sha1 a8930d5b…`). Бэкапы оригинала: `/tmp/kilo/_battle_city.base.nes`, `/tmp/kilo/bank_FF.base.asm`.

### 4m. Точный порт коллизии пули sub_E604 (эта сессия) — ВСЕ стадии 1-6 100%
Предыдущие попытки (квадрант вместо половины, без соседей, current+next) ломали стадии 1-5,
т.к. не воспроизводили sub_E604. Точный механизм (по ASM + PC/write-трассировке):
- Пулю коллизия проверяет в **4 позициях вдоль перпендикулярной оси** (смещения от текущей
  позиции: `+4·c`, `-c`, `-5·c`, где `c` — магнитуда скорости коллизии `|tbl_EA4D/tbl_EA49[dir]|`,
  всегда 1). Знак задаётся ЯВНО (не зависит от направления): sweep по X для up/down (dir 0/2),
  по Y для left/right (dir 1/3).
- В каждой задевшей позиции `sub_E69A/sub_D743` снимает **один квадрант** (`tile & ~quadrant`,
  `quadrant = 1<<(2*!!(y&4)+!!(x&4))`), либо разрушает полностью при `property bit1` (sub_E69A
  bra_E6EB). За счёт 4 позиций пуля у границы строки разрушает тайл над/под собой (напр. пуля
  вправо на y=72 рушит и (col,row9) TL+BL, и (col,row8) BL).
- Проверки `+4·c` и `-5·c` выполняются только если `base`/`-c` задели тайл (гейт в ASM).
- Старый `_bulletCollide` проверял только текущую клетку + перпендикулярного соседа с суб-ячейкой
  от ГЛОБАЛЬНОЙ позиции пули (для соседа суб-ячейка неверна) — из-за этого пуля не дожигала
  кирпич на границе (стадия 3: (8,20) 0xc vs 0x8; стадия 6: (22,23)/(23,23)).
- **Результат: ВСЕ стадии 1-6: враги 100% И поле 100% (таб. ниже).**
- Побочный эффект: `brickHit` (половинная модель) в `_bulletCollide` больше не используется
  (квадранты по суб-ячейке), но остаётся в `game-view.js` для ИИ.

### 4n. Призы и убийства врагов DEF-пулями (эта сессия, Фаза 5)
Портирована реакция врагов на пули игрока (DEF) по ASM:
- **`_bulletVsTank` разбит на два прохода** (порт `sub_E70C`):
  1) вражеские пули (слоты 2-7) vs DEF-танки: каска/шлем (`helmet`) гасит пулю без урона,
     иначе взрыв игрока `0x73` и сброс его типа;
  2) пули игрока (слоты 0,1) vs враги: **бонус при ударе по мигающему** (`type&0x04`, сразу,
     `sub_E8BE`), **броня** (`type&0x03`) — `DEC type`, враг жив (несколько попаданий),
     иначе взрыв врага `0x73`; спец-случай `0xE4` → `0xE2` (снять flash + броня -1).
- **Бонус перенесён с смерти на удар**: раньше `_onEnemyDead` спавнил приз при смерти,
  в эмуляторе — при попадании (`sub_E7D7`). `_onEnemyDead` теперь только декрементит `enemiesLeft`.
- **Взрыв `0x73`** (а не `0x70`): длительность до смерти **48 кадров** (24 тика с гейтом движения
  каждые 2 кадра; спец-переход `0x20→0x16`, `CMP #$10; ORA #$06`) — сверено с эмулятором 1:1.
- **Синк DEF-пуль** (`synced`): DEF-пули синкаются из эмулятора, `_moveBullets` обрабатывает для
  них только коллизию (разрушение кирпичей — тот же `sub_E604`, уже 100% на стадиях 1-6).
- **Призы**: `_bonus` подбор теперь требует `movementRange` (sub_E972); `_applyPrize`: часы →
  `clock=0x0A` + декремент каждые 64 кадра (`_clockHandler`, sub_DBF1 DC00), граната → взрыв всех
  врагов (`flag 0x73` + сброс типа, `EA17`), лопата уже была.
- **Юнит-тесты**: 100/100 зелёные (добавлены: удар мигающего → бонус; броня `0xE3`→`0xE2`;
  `0xE4`→бонус+`0xE2`; DEF-пуля убивает врага (полный цикл); приз-часы; приз-граната; подбор).
- **`scripts/def-kill-verify.mjs`** — диагностика Фазы 5 (DEF active): симулятор предсказывает
  врагов, но НЕ решение DEF-ИИ о выстреле, поэтому fire-frame kill (пуля убивает в кадр выстрела)
  не успевает обработаться → убийств меньше (напр. 5/9), рассинхрон поля/RNG. Не гарантирует 100%;
  сама логика смерти врага (броня/бонус/взрыв/enemiesLeft/приз) покрыта юнит-тестами.

### 4o. Запуск ИИ на симуляторе (эта сессия)
Слой для прогона существующих ИИ (tactical/scan/lookahead) на BattleSim вместо эмулятора:
- **`sim.toMem()`** — RAM-совместимый буфер из семантики сима (поле→0x400, танки→0x90/0x98/0xa0/0xa8,
  пули→0xcc/0xb8/0xc2, счётчики→0x80/0x82/0x0100, приз→0x88/0x86/0x87). ИИ, читающие mem,
  работают без изменений. **`sim.view()`** = `readState(toMem())` (GameState).
- **`sim.attControl`/`sim.defControl`** — внешнее управление ИИ: функция или Map `{idx: {dir, fire}}`.
  Реплика PvP net-dir/net-fire (sub_net_enemy_dir / sub_net_enemy_dir_store / sub_net_enemy_fire_check):
  - враг: направление ИИ применяется на точках решения (0x90 при `rng&1==0`, 0xA0 при
    `rng&0x0f==0` — RNG потребляется всегда, как в ASM), огонь — при netFire без RNG.
  - DEF: движение каждый кадр по вводу (без RNG, canLead), респавн вверх 0xa0 + шлем (tbl_E47E),
    жизни/re-спавн (`_onPlayerDead`), огонь по defControl.
- **`scripts/ai-verify.mjs [stage] [frames] [attAI] [defAI]`** — покадровая сверка ИИ: эмулятор
  (источник решений) → захват NET_DIR/NET_FIRE + кнопок DEF (перехват `_setDefController`) →
  кормление в сим → сверка всех танков+поля+RNG.
  Результат: **вражеский инжект 100%** для plan/scan/js (при DEF idle); lookahead — редкий
  edge-case поля ~f1332 (сим не уничтожает пулю врага 2 при bullet-vs-tank, когда DEF-танк в
  определённом состоянии). DEF-симуляция — частично: остаточный one-frame сдвиг респавна игрока
  (игровой гейт чувствителен к битам 0-1 $0B, вражеский — только к bit0, поэтому gateFrmLo
  (пост-кадровый) корректен для врагов, но для игрока сдвинут) + повороты/коллизия игрока.
- **Доводка DEF (эта сессия)**: исправлены респавн-направление игрока (вверх 0xa0 + шлем),
  DEF-движение по вводу без RNG, snap перпендикулярной оси при повороте, флаг «заблокирован» 0xa0,
  **fire edge-trigger** для DEF-пуль (эмулятор стреляет по фронту нажатия A — это закрыло
  lookahead edge-case и пере-выстрелы DEF), **bullet-vs-tank → explode 9** (вместо мгновенного
  удаления, как sub_E70C), ice-слайд DEF.
  Результат `ai-verify`: **plan и lookahead — 100%** на стадиях 1/3; scan — ~1050 кадров;
  js — ~281 (DEF tank0 в 0x80-паузе — коллизия корпуса/маркер в конкретной позиции).
  Осталось (DEF edge-cases, общий корень — субпиксельная коллизия DEF-пули):
  - **scan ~1050**: DEF-пуля 1 в эмуляторе взрывается на (97,192) (попадание в танк, клетки пусты),
    сим пропускает её дальше → из-за дрейфа DEF-танк подбирает гранату (id 4), взрывающую врагов.
  - **js ~281**: DEF-танк 0 заблокирован в эмуляторе на (88,192) (0x80-пауза), сим пропускает —
    потому что сим разрушает кирпич (25,11) DEF-пулей на кадр раньше/иначе, чем эмулятор.
  Требуется точный разбор bullet-vs-tank/brick DEF-пули на субпиксельных границах
  (sub_E604/sub_E70C для траекторий DEF-пуль).
  Добавлен гейт DEF-огня по пред-кадровому слоту эмулятора (defSlotBusy) — семантически корректен.
  **ATT-пуля vs DEF-танк оставлена `alive=false`** (не explode) — иначе stage-verify 1 не
  разрушает орла (bullet-тайминг); DEF-пуля vs враг — explode 9 (как sub_E70C). Это дало
  стадии 1-6 100% + plan/lookahead 100% в ai-verify.
- **`scripts/ai-eval.mjs [stage] [frames] [attModes] [defModes]`** — оценка ИИ на симе: ИИ читает
  `sim.toMem()`, сим исполняет, собираются метрики (убийства, HQ, исход, кадры). Детерминированно.
- **`scripts/emu-eval.mjs [stage] [frames] [attAI] [defAI] [defMode]`** — оценка ИИ защитника на
  ЭМУЛЯТОРЕ (эталон): кадры, убийства, HQ, исход. Использован в §4p для сверки сима и эмулятора.
- Юнит-тесты: toMem/view, attControl (net-fire, net-dir), 107/107.

### 4p. Эксперимент: улучшение ИИ защитников субагентами (эта сессия)
Запущены 3 параллельных субагента (Agent Manager, изолированные приватные каталоги), каждый

больше убить / пройти уровень.

**Улучшения (субпиксельно-обоснованные, конкретные методы):**

- **scan (`scanPlan`-def)**: `DEFEND_RADIUS=15` — реагировать на focus только если сам недалеко от

**Результат в СИМУЛЯТОРЕ** (база → улучшение, att=plan): plan 0→2 убийств (game_over@2353→timeout@6000),

plan 11→8 убийств, scan HQ разр. (база HQ цел), lookahead game_over (база timeout, HQ цел).

стрельбу → меньше убийств.

### 8c. Контракт атакующего + standalone-физика (эта сессия) — найден и исправлен РЕАЛЬНЫЙ баг
Задача сессии: контракт решений АТАКУЮЩЕГО и standalone-физика (ai-eval vs emu-eval).

**КРИТИЧЕСКИЙ ФИКС ПРЕДПОСЫЛКИ — emu-eval «plan» НЕ запускал JS-план**: в `pvp.js` диспетчер
атакующего мозга запускал JS только для режимов `"js"`/`"scan"`/`"lookahead"` — режима `"plan"`
НЕ БЫЛО (тактический мозг живёт под именем `"js"`). Поэтому `emu-eval 1 ... plan plan` молча
запускал NATIVE ASM-ИИ атакующего (9 убийств), а не JS-план (6 убийств). Вся предпосылка
«4 vs 9» была неверной (разные мозги). **Фикс**: `pvp.js` — добавить `"plan"` как синоним
`"js"` (тактический план). `emu-eval plan` теперь = 6 убийств (совпадает с `js`).

**Найден и исправлен РЕАЛЬНЫЙ баг standalone-физики — счётчик кадров $0A/$0B**:
- В эмуляторе `ram_frm_cnt_hi` ($0A) инкрементируется КАЖДЫЕ 64 кадра (при переходе $0B через
  0x00/0x40/0x80/0xC0), а НЕ каждые 256. Т.е. $0A = frame_count>>6, $0B = frame_count&0xff.
  Порт PRNG (sub_D44D) использует $0A + $0B.
- Симулятор в STANDALONE-режиме делал `frame = frame+1` (16-битный счётчик) → на $0B=0x40..0xC0
  $0A не инкрементировался → standalone RNG расходился уже с ~f96 (sim=143 vs emu=144).
- **Фикс**: `BattleSim.advanceFrame()` — инкрементирует frame с паттерном эмулятора ($0A растёт
  на 1, когда new $0B кратен 0x40). ai-eval/diag-standalone используют advanceFrame. Результат:
  **standalone сравнение plan/plan совпадает 3435 кадров (было 116)**, RNG синхронен до конца.
- Сопутствующее: `sim.defFrame` — отдельный ПРОСТОЙ счётчик (ритм респавна DEF, `_frame` pvp.js),
  а `sim.frame` — $0A/$0B-кодированный. planDefense получает `sim.defFrame` (для frame%30).

**Диагностика**:
- `scripts/diag-att.mjs` — контракт решений АТАКУЮЩЕГО (plan на toMem vs NET_DIR/NET_FIRE эмулятора)
  в lockstep. Вывод: контракт ЧИСТ до расхождения физики (решения совпадают, RNG расходится).
- `scripts/diag-standalone.mjs` — покадровое сравнение ДВУХ standalone-прогонов (эмулятор vs сим,
  каждый сам считает свои решения). Находит первый кадр расхождения танков/поля/RNG.

**Остатки (после advanceFrame) — отдельные точки расхождения на каждый режим атакующего**:
- **plan f3435** — ПАТОЛОГИЧЕСКИЙ ФРИЗ sub_E8BE (известный, §8b): DEF-пуля в мигающего врага,
  приз всегда на неподвижном DEF-tank0 → ретрай переезжает на следующий кадр. ДОРАБОТАН порт:

## 21. Фикс рассинхрона при фоновой вкладке (пауза матча)

**Симптом**: при перекрытии вкладки друг другу — движения игроков рассинхронизировались (и, вероятно,
отсюда же «танки в стенах»: рассинхроненное состояние рисует танки поверх кирпичей).
**Причина**: у скрытой вкладки останавливается `requestAnimationFrame` → клиент перестаёт шагать,
соперник «убегает» дальше окна rollback (~120 кадров) → необратимый desync.
**Решение**: пауза матча при `visibilitychange` — скрытая вкладка шлёт `pause`, обе стороны
останавливают симуляцию; при возврате — `resume`. Плюс лимит догона шага (2 кадра/rAF).
- `backend/signaling/relay.js`: `pause`/`resume` → рассылка `paused`/`resumed` участникам матча.
- `frontend/src/engine/lobby-client.ts`: `pauseMatch/resumeMatch` + `onPaused/onResumed`.
- `App.tsx`: `matchIdRef/pausedRef`; `onlineAdvance` не шагает на паузе; эффект `visibilitychange`
  шлёт pause/resume; оверлей «ПАУЗА».
- `GameCanvas.tsx`: `online.paused` + баннер `⏸ ПАУЗА`.
**Проверка (Playwright, 2 контекста)**: после старта оба на кадре 235; Алиса в фон → оба замерли
(235/235); возврат → оба возобновились (295/295). Кадры у обоих всегда равны → рассинхрона нет.

**Про коллизии**: проверил — JS-коллизия (`runtimePassable`/`canLead`) кирпичи блокирует,
ASM-патч сетевого ввода (`sub_net_enemy_dir`) задаёт только направление, а движение/коллизия идут через
общий `sub_DBF1_tank_movement` — обхода коллизии нет. Headless-тесты (челов. танк 900 кадров; онлайн-
lockstep 400 кадров × 8 танков) — 0 нарушений, `desync=0`. Вывод: «проход сквозь стены» — следствие
рассинхрона от фоновой вкладки; фикс паузы должен устранить. Если повторится БЕЗ перекрытия вкладок —
сообщите, буду копать ASM.
- Тесты: backend 9/9, frontend tsc+build; контейнер пересобран (:8080).

## 22. Фикс «танки проходят сквозь стены» (реальный баг коллизии)

**Воспроизведено** headless: при УДЕРЖАНИИ направления человеческий атакующий танк центром заезжает
в кирпич (147 кадров из 4000); у ИИ/ASM — 0. Метрика: центр танка в СУБ-КЛЕТКЕ (квадранте) кирпича.
**Корневая причина**: коллизия `sub_DC97` (и её JS-копия `canLead`) проверяет только **2 угла**
передней кромки (±8 от центра по перпендикуляру). Если центр танка НЕ на границе тайла (x%8 не 0 /
y%8 не 0), кирпич ровно впереди ПО ЦЕНТРУ не проверяется → танк проникает в него. ИИ меняет
направление только на выровненных позициях (x%8==0,y%8==0), поэтому у ИИ это почти не проявляется;
человек же свободно встаёт на x%8 != 0.
**Фикс**: `emulator-core/pvp.js` — для JS-оверрайда человеческого танка добавлен `stepTankStrict`:
3-я точка — ЦЕНТР передней кромки (в дополнение к 2 углам ASM). Танк не заезжает в стену.
**Проверка**: человеческий танк — 147 → **0** нарушений (4000 кадров); ИИ — 0; emulator-core **175/175**,
qa **29/29** (golden-state цел), netcode **5/5**; браузерный E2E (Боб держит «вверх») — остановился на
пустом тайле, оба клиента совпадают. Контейнер пересобран (:8080).
**Примечание**: у ASM-коллизии ИИ та же 2-точечная «слепая зона», но в тестах ИИ её не проявлял
(поворот только при выравнивании). Если ИИ всё же будет проходить — потребуется патч ASM `sub_DC97`
(добавить центр передней кромки) + пересборка ROM и byte-diff регрессия.

### 22a. Анти-застревание для ВСЕХ танков (unstick)
Строгий шаг помог только человеческому танку (JS-оверрайд). У ИИ-танков движение в ASM с той же
2-точечной «слепой зоной». Добавил в `pvp.js` детерминированный пост-шаг для всех живых танков:
если центр пиксельной суб-клетки солиден — выталкиваем танк назад по направлению взгляда (до 4 px).
Читает только RAM → одинаково у обоих клиентов, синхронность не нарушается.
Проверка: чисто-ИИ 10000 кадров — 0; человеческий + ИИ (4000) — 0; emulator-core 175/175, qa 29/29
(golden-state цел), netcode 5/5. Контейнер пересобран. Примечание: тело танка всё ещё может
визуально перекрывать кирпич у кромки (это штатная фронт-кромочная коллизия Battle City).

## 23. Фикс «разрушенные кирпичи не исчезают с экрана» (КОРНЕВАЯ ПРИЧИНА)

**Симптом (онлайн)**: защитник/атакующий простреливает кирпич, коллизия становится проходимой (танк
проезжает), но кирпич ВИЗУАЛЬНО остаётся на экране.
**Корневая причина**: PPU рендерит BG из объектов `this.nameTable[]` (tile/attrib), а `vramMem` — это
отдельная копия. Записи в nametable идут через `nameTableWrite` (обновляет ОБА). Но `nameTable[]`
**не входит в `JSON_PROPERTIES`** ppu → бинарный `saveState/loadState` (`io/state-codec.js`) его не
сохранял. При **rollback** (только онлайн) восстанавливались `cpu.mem`/`vramMem`, а рендер-кэш
`nameTable` оставался от «будущего» кадра → разрушенные кирпичи висели на экране. В solo rollback нет —
поэтому там баг не проявлялся.
**Фикс**: `io/state-codec.js` — `nameTable[].tile/attrib` сериализуются в снапшот и восстанавливаются
**in-place** (`nt.tile.set(...)`), сохраняя ссылки объектов, которые держит рендер.
**Проверка**: `tests/state-nametable.test.js` (round-trip nameTable + согласованность с vramMem);
emulator-core **177/177**, netcode **5/5**, qa **29/29**. Контейнер пересобран (:8080).

## 24. КОРНЕВАЯ ПРИЧИНА «кирпичи не исчезают»: баг бинарного кодека состояния

**Найдено наблюдателем** (headless онлайн-lockstep с задержкой + разрушение кирпичей):
`$0400` уменьшается, а `nameTable` (РЕНДЕР BG в PPU) замерзает → «призраки» кирпичей.

**Корень**: `io/state-codec.js` сериализовал типизированные массивы через `w.bytes(v)` /
`cur.set(v)` — а `TypedArray.set` **поэлементный**. Для `Uint16Array` (PPU `vramMirrorTable`,
32К элементов) и `Uint32Array` (`buffer/bgbuffer/pixrendered`) это теряло старшие байты.
После `loadState` (rollback) `vramMirrorTable` был мусором → `mirroredWrite` отправлял записи
поля в **pattern-таблицы вместо nametable** → разрушенные кирпичи не перерисовывались.

**Фикс**:
- `writeValue`: для typed-array пишем БАЙТОВОЕ представление (`new Uint8Array(v.buffer, ...)`).
- `decodeProps`: копируем БАЙТЫ в буфер целевого массива (in-place, сохраняя тип).
- Плюс `nameTable` (рендер-кэш PPU) явно сериализуется/восстанавливается in-place.
- Транзиентные кадровые буферы (`buffer/bgbuffer/pixrendered`) исключены из снапшота
  (пересоздаются рендером) → размер снапшота 915КБ → **174КБ**.

**Проверка**: наблюдатель призраков на 2000 кадров онлайн-rollback: было 2386 кадров/223
призрака, стало **30 транзиентных (макс 2) / финал 0** (задержка рендера на 1 кадр при откате).
emulator-core **177/177** (+3 теста `state-nametable.test.js`), netcode **5/5**, qa **29/29**.

# §26. Сессия 2026-09-10 — реконнект, UX соединения/десинка, основа 2v2

## 26a. Протокол v2 (`netcode/protocol/frame.js`)
- Все пакеты теперь с байтом-тегом `PKT` (INPUT/BATCH/HASH/PING/PONG/SNAP_REQ/SNAP) —
  устранена неоднозначность маршрутизации.
- `BATCH` — избыточная отправка последних N кадров + `headFrame` (следующий кадр отправителя).
- `PING`/`PONG` — измерение задержки.
- `SNAP_REQ`/`SNAP` — передача полного `saveState()` кусками по 16 КиБ (`encodeSnapshot`).

## 26b. Rollback-сессия (`netcode/rollback/session.js`)
- **Избыточность ввода** (`redundancy`, по умолчанию 4): потеря одиночного пакета
  восстанавливается без необратимого desync (дедупликация ввода по порту).
- **Задержка**: ping/pong, событие `latency {ms}`, `peer-unresponsive` (нет pong > 600 кадров).
- **Реконнект**: `rebindTransport(transport)`; события `transport-closed` / `transport-rebound`.
- **Desync-recovery**: не-авторитет (меньший `playerId` или явный `authority`) при расхождении
  хэшей запрашивает снапшот, применяет его (`resync`) и **догоняет** по `headFrame`
  (`catch-up`), пропущенные кадры симулируя с предсказанием (rollback исправляет их).
  События: `desync`, `resync-request`, `snapshot-sent`, `resync`, `catch-up`.

## 26n. Оптимизация rollback: пропуск «пустых» откатов
- **`netcode/rollback/session.js`**: ведём `remoteUsed` (ввод соперника, реально применённый
  при симуляции каждого кадра). При позднем вводе откат выполняется ТОЛЬКО если он отличается
  от предсказанного (`_remoteEqual`); иначе — `rollback-skipped` (счётчик `skippedRollbacks`).
  Это убирает лишнюю пере-симуляцию (CPU) и часть визуальных «прыжков» удалённого танка при
  постоянном/повторяющемся вводе, не меняя детерминизм.
- **Тесты**: netcode **13/13** (+тест «постоянный ввод не вызывает лишних откатов»),

## 26p. In-memory патчинг оригинального ROM (архитектура)
Оригинальный ROM теперь загружается как есть, а PvP-патчи применяются в памяти ядра
до `createMapper()` (mapper копирует PRG в `cpu.mem`). Дисковый `rom/disasm/_battle_city.nes`
остаётся генерируемым артефактом/эталоном для старых тестов.

### Модуль `emulator-core/patching/`
- `rom-image.js` — доступ к PRG как к образу: `map(addr)->{bank,offset}`, read/write/verify,
  `isFill` (свободные 0xFF-зоны), `fingerprint()` (FNV-1a32 PRG).
- `descriptor.js` — валидация дескрипторов + хелперы `hex/bytes/jmp/jsr/fill/composeSets`.
- `linker.js` — таблица символов, размещение рутин (`at` или first-fit в free-зонах),
  проверки NO_SPACE/OVERLAP и «зона пустая».
- `apply.js` — `applyPatchSet(rom, "pvp")`: проверка базы (mapper/банки/отпечаток), размещение
  рутин, проверка ВСЕХ `expect`-байтов, затем атомарная запись; отчёт
  `{setId,fingerprint,applied,routines}`.
- `errors.js` — типизированные коды (`PATCH_BASE_MISMATCH/EXPECT_FAILED/OVERLAP/NO_SPACE/...`).
- `patches/base-nrom.js` — база (mapper0, 1×16K, PRG FNV `b8a818c1`, sha1 `941ad7ca…`),
  таблица символов (RAM/ROM-метки), свободная зона `$EF75-$EFFF`.
- `patches/pvp.js` — 6 рутин (фиксированные `at`) + 6 равновеликих хуков
  (PRNG `$D45A`; spawn `$DB48`; dir `$DDD4`; target `$DE72`; turn `$DE84`; fire `$E171`).
- `registry.js` / `index.js` — именованные наборы (`"pvp"`, `"base"`), публичный API.

### Интеграция
- `emulator-core/src/nes.js`: `loadROM()` применяет `opts.patchSet` после `rom.load()` и до
  `reset()/createMapper()`; результат в `this.patching`.
- `frontend/src/engine/emulator.ts`: `aiConfig.patchSet = "pvp"`.
- `frontend/public/rom/battle_city.nes` и `Dockerfile` — теперь ОРИГИНАЛ (`rom/original/_battle_city.nes`).

### Инструмент и тесты
- `scripts/extract-patches.mjs` — diff оригинал↔сборка; `--check` применяет набор и сверяет PRG.
- `emulator-core/tests/patching.test.js` (8): побайтовое воспроизведение собранного ROM,
  BASE_MISMATCH, повторное применение, EXPECT_FAILED, NO_SPACE/OVERLAP, UNKNOWN_SYMBOL,
  детерминизм «оригинал+патч == собранный ROM» по `getFrameHash()`.
- Итоги: emulator-core **186/186**, netcode 14/14, backend 22/22, qa 30/30, frontend 2/2 + build,

- Не сделано (следующие шаги): relocation внутренних переходов рутин (сейчас фиксированные

## 26q. Netcode-инвариант: cartridgeFingerprint в handshake
Отпечаток пропатченного PRG (FNV-1a32, `nes.patching.fingerprint`) теперь передаётся в
сигналинге и сверяется на сервере — матч не стартует, если у клиентов разные наборы патчей.
- **Backend**:
  - `Room.cartridgeFingerprint` + `acceptFingerprint(fp)` (первый задаёт, остальные должны совпасть;
    пустой fp не блокирует — совместимость со старыми клиентами).
  - `_onJoin` сверяет `cartridgeFingerprint` → `error: cartridge-mismatch`.
  - `Lobby`: `fingerprint` в записи игрока, `fingerprintsAgree()`, `representativeFingerprint()`;
    `startLobbyMatch` возвращает `cartridge-mismatch` и НЕ создаёт комнату при рассинхроне.
  - `Matchmaker.add(..., fingerprint)`: пары образуются только с одинаковым отпечатком;
    HTTP `/matchmake` и `/lobbies` (create/join) принимают `cartridgeFingerprint`.
- **Frontend**: `EmulatorDriver.cartridgeFingerprint()`; `LobbyClient.setCartridgeFingerprint()`
  (уходит в create/join/reconnect); `NetClient.setCartridgeFingerprint()` (matchmake + join);
  `App` проставляет отпечаток после загрузки ROM.
- **Тесты**: backend **25/25** (+2: лобби-старт при рассинхроне, пары matchmaker по fp;
  +1 WS: join в комнату с чужим картриджем → `cartridge-mismatch`).
- Итоги: emulator-core 186/186, netcode 14/14, qa 30/30, frontend build, online E2E 2/2.
  Контейнер пересобран, отдаёт оригинальный ROM (:8080).
- Остаток: relocation внутренних переходов рутин, полный отказ от дискового патченого ROM
  как рантайм-источника, удаление `_rngInjection`.

## 26r. Релокация рутин (символические операнды)
Рутины PvP переведены с «сырых» hex-байт на **токены** — операнды-адреса резолвятся линкером,
а не зашиты. Это делает новый код переносимым в любую свободную зону.
- `descriptor.js`: `byteLength(tokens)` (длина без резолва) и `compileTokens(tokens, resolve, selfAddr)`;
  токены `jmpT/jsrT/absT/selfJmpT/selfAbsT` (внешние символы, RAM-адреса, self±delta).
- `linker.allocate` считает длину по токенам; `apply` компилирует рутины с резолвом после размещения.
- `patches/pvp.js`: 6 рутин описаны токенами (`absT("ram_net_enemy_*")`, `jsrT("sub_E363…")`,
  `selfJmpT(2)` для внутреннего цикла respawn, `jmpT("bra_DDE4"/"bra_DB4F"/"loc_DE75"/"sub_D44D…")`).
- Golden-тест по-прежнему побайтово совпадает с собранным ROM (`fingerprint=94cb0636`) — релокация
  не изменила раскладку (фиксированные `at`).
- Новый тест `relocation: токены резолвят внешние и собственные адреса` (self и jsr по новому адресу).
- Итоги: emulator-core **187/187**, backend 25/25, netcode 14/14, qa 30/30, frontend build,
  online E2E 2/2. Контейнер пересобран, отдаёт оригинальный ROM (:8080).
- Остаток: полный отказ от дискового `rom/disasm/_battle_city.nes` как рантайм-источника (сейчас —
  эталон/golden для части тестов), `_rngInjection` оставлен как тест-хук (используется
  scripts/enemy-verify.mjs, scripts/full-match-verify.mjs).

## 26s. jsnes сделан неизменным (все правки вынесены в расширения)
Базовое требование: эмулятор и ROM — неизменные компоненты. ROM: файл `rom/original/_battle_city.nes`
(sha1 `941ad7ca…`) подаётся как есть, патчи применяются ТОЛЬКО к in-memory образу PRG.

### jsnes восстановлен до upstream
- `emulator-core/src` приведён побайтово к `vendor/jsnes/src` (upstream `github.com/bfirsh/jsnes`,
  коммит `b8a45d0`). Вернулись `src/index.js` и `src/browser/` (не используются, но на месте).
- Откатаны прежние 3 правки: `patchSet`/`patching`/`noRender` (nes.js), `noRender`+багфикс тайла
  (ppu/index.js), `index.js`.
- Guard-тест `tests/jsnes-pristine.test.js`: `emulator-core/src` == `vendor/jsnes/src` побайтово
  (падает при любой правке эмулятора).

### Расширения (без правок jsnes)
- `emulator-core/ppu-ext.js` — `BattleCityPPU extends PPU`:
  - `renderFramePartially` — headless-режим `noRender` (без пикселей, с сохранением
    `onSpriteRender/onBgRender`);
  - `renderSpritesPartially` — исправление 8x16-спрайтов (верхний тайл = `index & $FE`);
    метод скопирован из upstream + 1 изменённая строка (при обновлении jsnes — сверить).
- `emulator-core/pvp.js` — `PvPNes extends NES`:
  - `loadROM()` применяет `opts.patchSet` к образу PRG до `createMapper()`;
  - `reset()` после `super.reset()` ставит `BattleCityPPU`.
- Новые тесты `tests/ppu-ext.test.js`: 8x16 спрайт использует `$1B0/$1B1` (не `$1AF`),
  `noRender` не рисует пиксели, подкласс действительно переопределяет методы.
